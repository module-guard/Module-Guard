# 공개 근거 정책 evidence-v1 (#33/#34)

총점은 제공하지 않는다. 독립 평가 상태는 `not_independently_validated`이다.
GitHub: https://docs.github.com/en/rest/repos/repos#get-a-repository
Registry: https://developer.hashicorp.com/terraform/registry/api-docs

공식 공개 REST API만 사용한다. GitHub 인증 자격증명을 보내지 않고 public 응답만
허용한다. 호스트·경로를 고정하고 리디렉션을 따라가지 않는다. 응답 512KiB,
요청당 8초 제한, 서버 오류·일시 통신 오류 1회 재시도, 403/429 재시도 없음.
버전/시간 버킷(1시간)별 결과와 실패를 저장한다. 동시 저장은 unique constraint로
단일 스냅샷을 유지한다. 소유자만 Origin 검증과 rate limit을 거쳐 수집할 수 있다.
읽기와 이력은 기존 repository visibility를 적용한다. 원자료는 지정 필드만 보존한다.

manifest에서 SECURITY.md, README, test 파일 존재를 측정한다. 이것은 운영·문서 품질,
테스트 통과를 증명하지 않는다. GitHub archived는 명시적 보관 상태이며 pushed_at이
오래되었다는 이유로 관리 중단이라고 판단하지 않는다. 신규·작은 프로젝트에 활동량
점수를 부과하지 않는다. 별·다운로드는 인기도 영역이며 계산에 포함하지 않는다.

근거 충족률 = confirmed 수 / not_applicable 제외 항목 수 × 100. 이 값은 긍정적
근거 비율이 아니라 관측 가능성이다. false/0, 정보 부족, 실패, 미확인은 구분한다.
7일 경과 자료는 stale로 표시한다. 과거 기록의 충족률은 수집 당시 수치이다.
서명 실패·위험 진단은 평판으로 상쇄하지 않는다.

## 독립 평가 절차와 현황

`reputation-cohort.json`은 실제 평가 결과가 아닌 30개 표본의 모집 슬롯이다.
공급자 5개, 프로젝트 규모 2개, 신규/활성/보관 3개 층으로 나눈다. 보정/평가를
분리하고 동일 프로젝트가 두 집합에 들어가지 않게 한다. 2026-11-19에 슬롯의 module_url,
commit/tag, evidence_digest를 채웠고(근거 스냅샷은 `reputation-cohort-evidence/`)
reviewer_a, reviewer_b, disagreement는 아직 null이다. 두 평가자는 서로의
결과를 보기 전에 근거별 판단과 누락 이유를 기입한다(방법은 `reputation-review-guide.md`). 불일치는 원자료와 정책을
대조하여 기록하고 평가 집합으로 정책을 보정하지 않는다.

현재 확인: 동일 입력 결정성, 인기도 변경이 coverage에 영향 없음, 누락과 0 구분의
자동 회귀 테스트, 실제 30개 표본 수집과 digest, 집단별 결측률·민감도·결정성 측정
(`scripts/reputation_cohort.py analyze`, `reputation-cohort-report.md`). 아직 미실시: 두 평가자 판단,
일치도 수치(kappa·불일치율) 분석. 이를 완료로 주장하지 않는다. 실제 자료가 모이면 축별 불일치율,
Cohen's kappa(적용 가능한 범주형 항목), 신규·소규모 결측률을 보고하고 총점 공개를
별도 검토한다. 악의적 파일 생성으로 존재 지표를 조작할 수 있어 보안 등급으로
사용하지 않는다. 테스트 결과나 운영 수준을 이 지표에서 추론하지 않는다.

## 총점 공개 결정 (#52)

결정: 두 평가자의 독립 검증이 끝나고 아래 기준을 충족하기 전까지 총점은 공개하지 않으며 평가 상태는
`not_independently_validated`로 유지한다. API·DB·스키마는 바꾸지 않는다.

근거와 측정된 한계(2026-11-19 표본 30개, 상세는 `reputation-cohort-report.md`):

- 두 평가자 일치도는 측정되지 않았다. 불일치율·kappa는 `pending`이다.
- 충족률은 관측 가능성이다. 보안·문서·테스트·출처 축은 30개 모두 100%로 품질을 구별하지 못한다.
- 적용 가능한 지표가 없는 축(Registry URL의 유지보수 3건)이 충족률 0으로 보여 "해당 없음"과
  "확인 실패"가 구별되지 않는다. 이 한계는 서비스 변경이 필요한 후속 과제이다.
- 파일 존재 지표(`SECURITY.md`는 30개 중 22개 없음)는 성숙한 활성 모듈과 신생 모듈을 구별하지 못하고
  조직 수준 정책 파일을 인식하지 못한다.
- 실패 경로(요청 한도·출처 오류)는 실제 자료로 측정되지 않아 신규·소규모 결측률 0%를 일반화할 수 없다.
- 표본은 목적 표집이다. 대표성이 없고 30개로는 집단별 추정이 불안정하다.
- 인기도를 바꿔도 충족률이 변하지 않는 것은 구조상 보장이며 경험적 발견이 아니다.

총점 공개를 다시 검토하는 명시적 기준(전부 충족, 별도 후속 이슈에서 평가):

1. 30개 슬롯 모두 두 평가자가 독립 기입했고 `validate`가 통과한다.
2. 평가 집합에서 기입 쌍이 10개 이상인 모든 축의 kappa ≥ 0.61이고 불일치율 ≤ 20%이다. 기준은
   평가자 값을 보기 전에 고정한 초기 제안이며 평가자 값을 본 뒤 바꾸지 않는다. kappa가 정의되지 않는 축은
   기준 미충족으로 본다.
3. 모든 불일치의 원인을 원자료·정책과 대조해 기록했고 정책·근거 문제에서 나온 수정은 새 정책 버전과 새
   평가 집합으로 다시 검증했다(평가 집합으로 정책을 보정하지 않는다).
4. 해당 없음과 확인 실패가 충족률에서 구별된다(위 한계 해소).
5. 신규·소규모 집단의 축별 평균 충족률 차이가 구조적 원인을 제외하고 10%p 이하이고, 인기 조작 민감도
   검사(`analyze`)가 통과한다.
6. 가중치·총점 방식의 타당도를 소비자 판단 결과 등 외부 근거와 비교한 검증이 있다. 이 이슈의 범위 밖이다.
7. 서명 실패·중대 위험을 평판으로 상쇄하지 않는 규칙이 총점에도 적용된다.

총점을 공개하기로 하면 API 필드는 추가만 하고 기본값을 둔다. DB 마이그레이션은 팀 합의 전에는 하지 않는다.
검증 없이 정확도를 단정하지 않는다.
